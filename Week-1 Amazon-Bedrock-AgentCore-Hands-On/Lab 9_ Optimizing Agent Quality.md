## [Overview](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#overview)

In Lab 5 you set up continuous evaluation and learned how well your agent performs. But knowing your `GoalSuccessRate` is 72% doesn't tell you *how* to get to 90%. Rewriting a system prompt or sharpening tool descriptions by hand is slow guesswork.

**AgentCore Optimization** closes that gap. It turns the real traces and evaluation scores you already produce into concrete, AI-generated improvements, and then lets you validate those improvements on live traffic before you commit to them.

This lab uses everything you've already built. You'll optimize the exact `CustomerSupport` agent, its real system prompt, and its real tools.

### [How the optimization loop works](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#how-the-optimization-loop-works)

AgentCore Optimization connects evaluation findings to validated improvements through a repeatable cycle:

```bash
1
2
3
4
5
6
7
1. Generate a recommendation   → point the service at traces + a target evaluator
                                  → get an optimized system prompt or tool descriptions
2. Package as a config bundle   → a versioned, immutable snapshot of the config
3. Validate with an A/B test    → split live traffic (control vs treatment) via Gateway
                                  → online evaluation scores each session
4. Promote the winner & repeat  → route 100% of traffic to the winner
                                  → new traces become the baseline for the next round
```

## [Step 1: Make Sure You Have Traces to Analyze](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#step-1:-make-sure-you-have-traces-to-analyze)

Recommendations analyze real session traces. If you generated interactions in Lab 5, you already have data. To be safe, send a few more varied requests so the engine has recent sessions that exercise every tool — including some ambiguous ones that tend to trip the agent up.

**Why --runtime CustomerSupport?**

Since Lab 8 added a Harness agent to your project, `agentcore invoke` no longer knows which agent to target by default. You now need to specify `--runtime CustomerSupport` for the coded agent or `--harness OrderResearchAgent` for the zero-code one.

- **macOS/Linux**
- **Windows**

```bash
SESSION_OPT=$(python3 -c 'import uuid; print(uuid.uuid4())')

# Clear product question
agentcore invoke "What's the price and battery life of the Smart Watch?" \
  --runtime CustomerSupport --session-id $SESSION_OPT --bearer-token "$TOKEN" --stream

# Return vs. technical support ambiguity ("broken product")
agentcore invoke "My headphones are broken. What should I do?" \
  --runtime CustomerSupport --session-id $SESSION_OPT --bearer-token "$TOKEN" --stream

# Warranty via Gateway
agentcore invoke "Is PROD-002 still under warranty?" \
  --runtime CustomerSupport --session-id $SESSION_OPT --bearer-token "$TOKEN" --stream

# Multi-intent request
agentcore invoke "I want to return my USB-C Hub and also check if it's under warranty." \
  --runtime CustomerSupport --session-id $SESSION_OPT --bearer-token "$TOKEN" --stream

# Vague request with no product named
agentcore invoke "It stopped working. Can I get my money back?" \
  --runtime CustomerSupport --session-id $SESSION_OPT --bearer-token "$TOKEN" --stream
```

**Give CloudWatch a moment**

Wait 2–5 minutes after invoking for CloudWatch to ingest the telemetry before starting a recommendation. The recommendation engine reads traces from CloudWatch Logs.

## [Step 2: Generate a System Prompt Recommendation](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#step-2:-generate-a-system-prompt-recommendation)

**Recommendation names are unique per account**

If you get a 409 error ("A recommendation with name already exists"), it means you've run this before. Either use a different `--run` name (e.g., `cs-prompt-rec-2`) or delete the existing one with `agentcore delete recommendation <name>` before re-running.

Now ask AgentCore to analyze your traces and propose a better system prompt. You pass your **current** system prompt (so the recommendation is a superset that preserves your intent) and a **target evaluator** — the reward signal the optimizer pushes toward. We'll use `Builtin.GoalSuccessRate`, the same evaluator from your `QualityMonitor` config in Lab 5.

- **macOS/Linux**
- **Windows**

```bash
1
2
3
4
5
6
7
8
agentcore run recommendation \
  --type system-prompt \
  --run cs-prompt-rec \
  --runtime CustomerSupport \
  --evaluator Builtin.GoalSuccessRate \
  --inline "You are a helpful and professional customer support assistant for an e-commerce company. Provide accurate information using the tools available to you. Be friendly, patient, and understanding. Always offer additional help after answering. Always use tools to get accurate information rather than guessing." \
  --lookback 7 \
  --wait
```

**What the flags mean:**

| FlagPurpose                 |                                                                               |
| --------------------------- | ----------------------------------------------------------------------------- |
| `--type system-prompt`      | Generate an optimized system prompt (vs. `tool-description`)                  |
| `--run`                     | A name for this recommendation job                                            |
| `--runtime CustomerSupport` | The CLI resolves the log group ARNs and service name from this runtime        |
| `--evaluator`               | The single target evaluator used as the optimization signal                   |
| `--inline`                  | Your current system prompt to optimize (or use `--prompt-file ./prompt.txt`)  |
| `--lookback 7`              | Analyze traces from the last 7 days via CloudWatch Logs                       |
| `--wait`                    | Block until the job reaches a terminal state instead of returning immediately |

`run recommendation` is asynchronous. With `--wait` the CLI blocks and prints the result when it's done. Without `--wait`, it returns a `recommendationId` you can retrieve later.

### [Review the result](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#review-the-result)

The output contains two key fields: `recommendedSystemPrompt` (the optimized prompt) and `explanation` (why the changes were made). If you want to inspect the full JSON later, you can retrieve it with `agentcore view recommendation cs-prompt-rec-XXXXXXXXXX --json` (using the full ID printed when the run completed).

Here's what the optimizer does under the hood: it examines your real traces, identifies which sessions scored well and which scored poorly on your target evaluator, finds patterns in the failures, and generates concrete rules to address them. For example, in our workshop traces the optimizer found:

- **Failure pattern:** When a user mentioned a product by name ("I just bought a Mechanical Keyboard"), the agent asked for a product ID instead of proactively searching with tools
- **Failure pattern:** When `<user_context>` tags contained facts about the user, the agent sometimes ignored them and claimed it had no information
- **Fix applied:** "When a user mentions a product by name, proactively search for it using tools. Use `<user_context>` tags and prior messages to inform responses; never ignore what the user already told you."

The optimizer also added a safety rule (confirm before real-world actions like refunds) that wasn't in the original prompt. The final recommended prompt preserves your original text verbatim and appends the new guidance below it.

Save the recommended system prompt to an environment variable — you'll use it as the **treatment** in the A/B test:

- **macOS/Linux**
- **Windows**

```bash
1
2
3
4
5
6
REC_ID=$(agentcore view recommendation --json | jq -r '.recommendations[0].id')
RECOMMENDED_PROMPT=$(agentcore view recommendation --json | jq -r '.recommendations[0].result.systemPromptRecommendationResult.recommendedSystemPrompt')

echo "Recommendation ID: $REC_ID"
echo "Recommended prompt:"
echo "$RECOMMENDED_PROMPT"
```

**Your results will vary**

The optimizer analyzes *your* traces, so the specific failure patterns and recommendations depend on the interactions you generated. The structure is the same: original prompt preserved + actionable rules derived from real failures.

## [Step 3: Generate a Tool Description Recommendation](https://catalog.us-east-1.prod.workshops.aws/event/dashboard/en-US/workshop/86-lab9-optimization#step-3:-generate-a-tool-description-recommendation)

System prompts aren't the only thing you can optimize. When an agent picks the wrong tool for an ambiguous request, sharper tool descriptions often fix it. A tool description recommendation analyzes tool-selection patterns directly from traces — no target evaluator required.

Pass your current tool names and descriptions (from Lab 1's `@tool` docstrings and Lab 3's warranty schema). Note that Gateway tools appear in traces with the target name prefix (`WarrantyCheck___check_warranty`), so use that full name here:

- **macOS/Linux**
- **Windows**

```bash
1
2
3
4
5
6
7
8
9
agentcore run recommendation \
  --type tool-description \
  --run cs-tool-rec \
  --runtime CustomerSupport \
  --tools "get_return_policy:Get return policy information for a specific product category (electronics, accessories, audio)." \
  --tools "get_product_info:Search for product information by name, ID (e.g. PROD-001), or keyword." \
  --tools "WarrantyCheck___check_warranty:Check the warranty status of a product by its product ID. Returns duration, status, and expiration date." \
  --lookback 7 \
  --wait
```

> ***Note:**** Unlike system prompt recommendations, tool description runs omit **`--evaluator`** entirely. The service infers confusion from how the agent actually selected tools in your traces.*

**ValidationException: tools not found in traces?**

If you get a `ValidationException` saying a tool (e.g., `check_warranty`) was "not found in the sampled agent traces," it means the recommendation engine's trace-sampling window didn't capture invocations of that tool. This can happen if the tool was called in older sessions outside the lookback window, or if the sampled subset of traces didn't include it. **Fix:** remove the failing tool from the `--tools` list and re-run with the remaining tools. You can always run a separate recommendation for that tool later after generating fresh traces that exercise it.

Review the output. The result contains a per-tool entry with the original description, a recommended replacement, and an explanation of what the optimizer found. To inspect the full JSON later, use `agentcore view recommendation cs-tool-rec-XXXXXXXXXX --json` (with the full ID from the run output). Here's the kind of improvements it generates:

| ToolWhat the optimizer foundRecommended change |                                                                                                                          |                                                                                                                                           |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `get_return_policy`                            | A trace showed the agent passing "electronics" instead of "accessories" for a USB-C Hub, returning the wrong policy      | Added: "Use the product's category (from `get_product_info`) to ensure the correct policy is retrieved"                                   |
| `get_product_info`                             | Agents prefer product IDs over names when IDs are available; tool is often called in parallel with warranty/return tools | Added: "Use the product ID (format: PROD-XXX) for precise lookups. Can be called in parallel with warranty check or return policy tools." |
| `WarrantyCheck___check_warranty`               | All calls succeeded; commonly paired with other product tools                                                            | Added: explicit return fields (status, expires date, format) and parallel-call guidance                                                   |

The optimizer derives these from actual failure patterns and usage patterns in your traces, not generic best practices. Each recommendation makes the tool description more precise so the model is less likely to call it incorrectly.
